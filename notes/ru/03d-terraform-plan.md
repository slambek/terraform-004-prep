# 3d. Generate and review an execution plan for Terraform

## What `terraform plan` Does (Default / "Normal" Mode)

1. **Refreshes** — читает текущее состояние уже существующих реальных объектов, чтобы state Terraform был актуальным.
2. **Diffs** — сравнивает обновлённый state с текущей конфигурацией.
3. **Proposes** — набор действий изменения, которые привели бы реальную инфраструктуру в соответствие с конфигурацией.

`plan` **никогда не вносит изменения** — он read-only по отношению к вашей инфраструктуре (хотя он обновляет in-memory/кэшированный state во время refresh и может записать это в state-файл, если вы явно сохраните через последующий `terraform apply` — сам plan не сохраняет изменения state на диск в normal-режиме).

Если ничего не нужно менять, `plan` сообщает, что никакие действия не требуются.

## Planning Modes (Mutually Exclusive)

| Mode | Flag | Goal |
| :--- | :--- | :--- |
| **Normal** (default) | *(none)* | Привести remote-систему в соответствие с конфигурацией. |
| **Destroy** | `-destroy` | Спланировать уничтожение всех реальных объектов, оставив пустой state. Эквивалентно `terraform destroy` (3f). |
| **Refresh-only** | `-refresh-only` | Только согласовать state/output-значения Terraform с изменениями, внесёнными в реальные объекты **вне** Terraform — не предлагает изменения, вызванные конфигурацией. |

Комбинировать режимы нельзя — активация одного отключает "normal"-режим, и режимы не могут сочетаться друг с другом.

## Planning Options

* **`-refresh=false`** — пропускает шаг refresh (быстрее, бережнее к API-запросам, но рискует дать неполный/некорректный план, поскольку внешний дрейф игнорируется). Нельзя комбинировать с `-refresh-only` (этот режим *и есть* refresh).
* **`-replace=ADDRESS`** — планирует destroy-and-recreate для конкретного resource instance, даже если конфигурация не менялась (например, деградировавший instance). Можно указывать многократно для нескольких ресурсов. Нельзя комбинировать с `-destroy`. (Заменяет устаревший `terraform taint`.)
* **`-target=ADDRESS`** — ограничивает планирование ресурсом/module instance и всем, от чего он зависит. **Только для исключительных случаев** — рутинное использование рискует необнаруженным дрейфом в других местах; предпочтительнее разбивать крупные конфигурации на более мелкие, применяемые независимо.
* **`-var 'NAME=VALUE'`** / **`-var-file=FILENAME`** — задают значения input-переменных из командной строки; `-var-file` обычно предпочтительнее `-var`, потому что вы избегаете головной боли с shell-экранированием для сложных типов (list/map/set требуют полного Terraform-выражения в качестве значения; примитивы — string/number/bool — это просто строка).

## Other Options (I/O and Reporting, Not Plan Content)

* **`-out=FILE`** — сохраняет план в бинарный файл, который позже можно передать в `apply`, чтобы выполнить *именно* эти действия. Без `-out` вы получаете **speculative plan** — только описание, без намерения применять (используется для ревью PR, см. 3a).
* **`-json`** — machine-readable вывод плана.
* **`-detailed-exitcode`** — `0` = нет изменений, `1` = ошибка, `2` = есть изменения. Полезно для ветвящейся логики в CI.
* **`-parallelism=n`** (по умолчанию `10`) — ограничивает число одновременных операций графа.
* **`-compact-warnings`** — сжимает вывод предупреждений до сводок.

⚠️ **Сохранённые файлы плана могут содержать sensitive-данные в открытом виде** (даже значения, скрытые в выводе терминала) — никогда не коммитьте файл плана (бинарный или JSON) в систему контроля версий.

## How Terraform Builds the Plan: The Dependency Graph

*(Продвинутая/фоновая тема — не требуется для рутинного использования, но концептуально встречается на экзамене.)*

Перед созданием плана Terraform строит граф:

* **Node types:** Resource Node (один на ресурс или на instance `count`/`for_each`), Provider Configuration Node (представляет полную конфигурацию provider'а), Resource Meta-Node (только удобство группировки, для `count > 1`).
* **Build order (simplified):** добавить resource nodes → присоединить provisioners → добавить явные рёбра `depends_on` → добавить "осиротевшие" ресурсы из state (ресурсы, удалённые из конфигурации, но всё ещё присутствующие в state) → сопоставить ресурсы с их provider configuration nodes → разобрать интерполяции/ссылки на атрибуты в рёбра зависимостей → добавить единственный корневой узел → разделить любой ресурс, для которого выполняется destroy-and-recreate, на отдельные узлы destroy/create (порядок destroy часто отличается от порядка create) → проверить отсутствие циклов и наличие единственного корня.
* **Walking the graph:** в глубину, **параллельно** там, где это позволяют зависимости — узел выполняется, как только завершились все его зависимости. Параллелизм ограничен `-parallelism` (по умолчанию 10). Это, однако, *не* то, как Terraform справляется с rate limits облачных API — providers (например, AWS) обычно реализуют для этого собственный backoff/retry.

Именно поэтому **цикл** (два ресурса, ссылающихся друг на друга, см. 3c) не проходит валидацию — граф нельзя обойти, если это не DAG.

## Anatomy of a Saved Plan File (`-json` view)

* **`terraform_version` / `format_version`** — гарантирует, что применяется та же версия Terraform, которая сгенерировала план.
* **`configuration`** — снимок вашей конфигурации *как она написана*, включая `provider_config` (с зафиксированными version constraints) и `root_module.resources` / `module_calls` (с зафиксированными перекрёстными ссылками, благодаря чему Terraform знает порядок операций).
* **`variables`** — зафиксированные значения input-переменных — **включая значения, помеченные `sensitive`**, хранящиеся в открытом виде. (Значения, заданные через переменные окружения, таким образом *не* фиксируются.)
* **`resource_changes`** — для каждого ресурса `actions` (комбинации `create`/`update`/`delete`/`replace`), значения `before`/`after`/`after_unknown`, и списки редактирования `before_sensitive`/`after_sensitive`.
* **`planned_values`** — итоговое ("after") состояние для каждого ресурса, структурированное как один чистый объект на ресурс (используется такими инструментами, как проверки политик Sentinel и оценка стоимости HCP Terraform).
* **`prior_state`** — присутствует только когда state-файл уже существовал до этого плана — снимок state ровно таким, каким он был до plan.

## Exam Quick Facts

* Поведение plan по умолчанию = **refresh → diff → propose**; сам по себе он ничего не меняет.
* Три взаимоисключающих режима: **Normal**, **Destroy** (`-destroy`), **Refresh-only** (`-refresh-only`).
* `-target` и `-replace` предназначены для **исключительных обстоятельств**, а не для рутинного workflow.
* Без `-out` → speculative plan (только просмотр). С `-out` → файл плана, который можно применить `apply` точно как есть.
* Файлы плана могут содержать **sensitive-значения в открытом виде** — никогда их не коммитьте.
* `-detailed-exitcode`: `0` нет изменений / `1` ошибка / `2` есть изменения.
