# 3c. Validate a Terraform configuration

## What `terraform validate` Does

`terraform validate` проверяет, что конфигурация **синтаксически корректна и внутренне согласована** — корректность имён атрибутов, типов значений, структуры блоков — используя только саму конфигурацию.

**Что она НЕ проверяет:**

* Внешние сервисы — она никогда не вызывает API providers.
* Remote state.
* Действительно ли input-переменным присвоены реально валидные значения (это работа `plan`, которая включает подразумеваемую проверку валидации *плюс* проверки относительно конкретного контекста запуска — целевого workspace, реальных значений переменных, state).

## Prerequisites

`validate` требует **инициализированную рабочую директорию** с установленными providers и модулями — сначала запустите `terraform init` (см. 3b). Если вам нужна только валидация без обращения к backend'у, можно инициализировать так:

```bash
terraform init -backend=false
```

## Usage

```bash
terraform validate
terraform validate -json     # machine-readable output for editor/CI integration
terraform validate -no-color
```

Её безопасно запускать автоматически и часто — например, как save-hook в редакторе или как шаг CI-теста для переиспользуемых модулей — потому что она никогда не трогает реальную инфраструктуру или remote state.

## `-json` Output Shape

JSON-объект включает:

* `valid` (bool) — общий результат.
* `error_count` / `warning_count` — всегда `0` ошибок, когда `valid` равно `true` (одни только warnings не делают конфигурацию невалидной).
* `diagnostics` — массив объектов, каждый с `severity` (`"error"`/`"warning"`), `summary`, `detail` и опциональным `range` (файл + начальная/конечная позиция в исходнике), указывающим на проблему.

## Common Errors Validate Catches

* **Cycle errors** — циклическая логика в графе зависимостей, например два ресурса `aws_security_group`, чьи блоки `ingress` напрямую ссылаются на ID друг друга. Terraform не может определить порядок создания, потому что каждый зависит от того, что другой уже существует.
  * **Fix pattern:** разорвите цикл, вынеся взаимозависимые правила из resource-блоков в отдельные ресурсы `aws_security_group_rule`, которые ссылаются на ID security groups — это позволяет сначала создать обе группы (без взаимозависимой конфигурации), а затем прикрепить правила.
* **Invalid reference / invalid `for_each` value** — например, использование splat-выражения (`aws_security_group.*.id`, которое даёт **list**) в качестве значения `for_each`, которое требует **map** или **set**. Исправляется получением map через блок `locals`.
* **Missing resource instance key** — ссылка на `aws_instance.web_app.id`, когда у ресурса задан `for_each`; Terraform требует индексирования конкретного instance (или `for`-выражения по всем instance, например `[for instance in aws_instance.web_app : instance.id]`), как только ресурс перестаёт быть single-instance.
* **Missing / unsupported argument** — несовпадающие аргументы после повышения версии модуля (новая версия модуля может требовать совершенно другие имена входных данных).

**Important:** Terraform останавливается на **первом классе ошибок**, который находит во время валидации — исправление одной ошибки и повторный запуск `validate` — это нормально; для сломанной конфигурации ожидайте несколько итераций.

## Exam Quick Facts

* `validate` = **только синтаксис + внутренняя согласованность** — без вызовов API providers, без state, без реальных проверок значений переменных.
* Сначала требует `terraform init` (или `init -backend=false`).
* `plan` включает подразумеваемую проверку валидации *плюс* реальный контекст provider/state — `validate` — это облегчённая, самостоятельная версия.
* Безопасно и дёшево запускать повторно/автоматически (хуки редактора, CI).
* Terraform сообщает и останавливается на одном классе ошибок за раз — ожидайте итеративные циклы исправление → повторная валидация.
