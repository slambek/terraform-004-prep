# 5b. Describe variable scope within modules

> **Scope note:** синтаксис самих блоков `variable`/`output`/`locals` (аргументы, `sensitive`, `validation` и т. д.) полностью разобран в **4c**. Эта заметка конкретно про то, *что пересекает границу модуля и как*.

## Each Module Has Its Own Isolated Namespace

Переменные, locals и имена ресурсов, объявленные в одном модуле, **не видны** в другом модуле — включая связь родитель-потомок. Дочерний модуль не может видеть значения `var.*` или `local.*` родителя просто потому, что он «вложен» в ту же конфигурацию; каждый модуль видит только:

* свои **собственные** объявления `variable` (заполненные тем, что передал вызывающий),
* свои **собственные** `locals`,
* свои **собственные** ссылки на ресурсы/данные,
* и outputs своих **собственных** дочерних модулей (через `module.<name>.<output>`).

## How Values Flow *In*: Module-Specific Inputs

Блоки `variable` модуля определяют его входной интерфейс. **Вызывающая сторона** передаёт значения как аргументы прямо внутри блока `module` — они сопоставляются по имени с объявленными переменными вызываемого модуля:

```hcl
# child module declares:
variable "bucket_name" { type = string }

# caller supplies it as a module argument:
module "website_s3_bucket" {
  source      = "./modules/aws-s3-static-website-bucket"
  bucket_name = "my-unique-bucket-2024"
}
```

Переменные без `default` становятся **обязательными аргументами** на блоке module — их пропуск это ошибка. Это полностью аналогично тому, как работают переменные root-модуля (4c) — единственное отличие в том, *откуда* берётся значение (аргумент блока `module` вместо `-var`/`.tfvars`/env vars).

## How Values Flow *Out*: Outputs Only

**Единственный** способ, которым данные покидают модуль — через его блоки `output`. Родитель ссылается на output потомка как `module.<LABEL>.<OUTPUT_NAME>`:

```hcl
output "vpc_public_subnets" {
  value = module.vpc.public_subnets
}
```

Если модуль явно не выводит значение через output, ничего об этом ресурсе не видно вызывающей стороне — даже косвенно. Именно поэтому продуманное проектирование outputs модуля важно не меньше, чем проектирование его inputs.

## Provider Configuration Is a Special Case: Implicit Inheritance

В отличие от переменных, **конфигурация provider'а не передаётся как обычный input** — дочерний модуль автоматически и **неявно** наследует конфигурацию provider'а по умолчанию от своего вызывающего. Именно поэтому **дочерние модули, как правило, не должны содержать собственные блоки `provider`** — пусть root-модуль конфигурирует providers, а каждый модуль-потомок переиспользует ту же самую конфигурацию.

Чтобы использовать **не-default (aliased)** конфигурацию provider'а внутри дочернего модуля, родитель должен явно замапить её через мета-аргумент `providers` на блоке `module`, а дочерний модуль должен объявить, что ожидает этот alias, через `configuration_aliases` в своём собственном блоке `required_providers` (механику alias см. в 2b):

```hcl
# root module
provider "aws" {
  alias  = "usw1"
  region = "us-west-1"
}

module "tunnel" {
  source    = "./tunnel"
  providers = {
    aws.src = aws.usw1
  }
}
```

## Design Pattern: Dependency Inversion

Поскольку модуль не видит ничего за пределами своих собственных объявленных переменных, хорошо спроектированные модули **принимают свои зависимости как input-переменные**, а не создают эти зависимости внутри себя. Например, модулю `consul_cluster`, которому нужны VPC и subnets, следует принимать `vpc_id` и `subnet_ids` как переменные, а не создавать собственный VPC — это сохраняет его пригодным для использования наряду с другой инфраструктурой, разделяющей ту же сеть, и позволяет вызывающей стороне позже подставить ID из ресурса, data source или совершенно другого модуля, вообще не меняя `consul_cluster`.

```hcl
module "consul_cluster" {
  source     = "./modules/aws-consul-cluster"
  vpc_id     = module.network.vpc_id
  subnet_ids = module.network.subnet_ids
}
```

## Data-Only Modules

Модулю вообще не нужны блоки `resource` — модуль, содержащий только `data`-источники (см. 4a), допустим и полезен для инкапсуляции того, **как** извлекается некоторая часть общей информации (например, запрос ID общей сети), так что вызывающим сторонам не нужно знать или беспокоиться о том, приходят ли эти данные из живого API-запроса, поиска через `terraform_remote_state` или чего-то ещё. Правила видимости идентичны: вызывающей стороне видно только то, что модуль, содержащий только данные, явно выводит через output.

## Exam Quick Facts

* Модуль не может видеть переменные/locals другого модуля — только **свои собственные**, плюс всё, что он явно объявляет как `variable`-inputs и импортирует через `module.<name>.<output>`.
* Значения попадают в модуль **только** как аргументы блока `module`, сопоставленные с объявленными переменными этого модуля.
* Значения покидают модуль **только** через блоки `output` — ничего неявного.
* Конфигурация provider'а — исключение: по умолчанию она **неявно наследуется** от вызывающего; явное задание alias требует и мета-аргумента `providers`, *и* `configuration_aliases` у потомка.
* Best practice: дочерние модули, как правило, **не должны** объявлять собственные блоки `provider`.
* Dependency inversion = принимать зависимости как переменные вместо их создания внутри — делает модули композируемыми.
