# 2d. Explain how Terraform uses and manages state

## Core Concept

Terraform **требует** state-файл для работы — это не опция. State — это база данных, которая позволяет Terraform знать, какой реальный объект соответствует какому resource-блоку в вашей конфигурации.

> **Scope note:** этот objective — *концептуальная* основа state. Типы backend'ов (local vs remote), state locking и workflow работы с drift — отдельные objectives экзамена — **Section 6 (6a–6d)**. Повседневные команды CLI для инспекции (`terraform show`, `state list`, `import`) относятся к **Section 7 (7a–7b)**; базовое использование `state mv` тоже в 7b, но его workflow миграции между state-файлами живёт в **6d**. Эта заметка покрывает только *зачем существует state и что в нём содержится*.

## Why Terraform Needs State

### 1. Mapping Configuration to the Real World

Resource-блок вроде `resource "aws_instance" "foo"` — это просто метка в вашей конфигурации. Terraform нужен способ узнать, что эта метка соответствует реальному объекту с ID `i-abcd1234`. State даёт этот маппинг.

* Ранние прототипы Terraform пытались использовать вместо state-файла облачные теги — это не сработало, потому что **не все ресурсы/providers поддерживают теги**.
* **Каждый реальный (remote) объект должен маппиться ровно в один resource instance.** Если один и тот же реальный объект привязан к двум resource instance, маппинг становится неоднозначным, и Terraform ведёт себя непредсказуемо.

### 2. Metadata

Помимо маппинга ID, state отслеживает метаданные, необходимые Terraform для корректной работы, включая:

* **Resource dependencies** — обычно выводятся из конфигурации, но если вы полностью удалите resource-блок, в конфигурации больше не будет этой информации. Terraform хранит копию последнего известного порядка зависимостей *в state*, чтобы всё равно знать правильный порядок для destroy.
* Указатель на то, какая **provider configuration** (включая aliases) использовалась для ресурса последней.

### 3. Performance (Attribute Caching)

State кэширует значения атрибутов каждого ресурса. При `plan` Terraform обычно опрашивает providers, чтобы обновить этот кэш и сравнить реальную инфраструктуру с конфигурацией.

* Для крупных инфраструктур обновление каждого ресурса при каждом запуске — медленно (round-trip'ы к API + rate limits), поэтому кэшированный state иногда рассматривается как источник истины (например, через `-refresh=false` или `-target`).
* Это кэширование — **самая необязательная** из ролей state — всё остальное (mapping, metadata) является жёстким требованием.

## What's Actually Inside the State File

State хранится в формате JSON (по умолчанию локально, `terraform.tfstate`). Структура верхнего уровня:

```json
{
  "version": 4,
  "terraform_version": "1.7.0",
  "serial": 18,
  "lineage": "0c41e079-...",
  "outputs": {},
  "resources": []
}
```

Каждая запись в `resources` фиксирует:

* `mode` — `"managed"` (resource-блок) или `"data"` (data-блок).
* `type` и `name` — например, `aws_instance` / `example`.
* `provider` — какой provider (и alias) им управляет.
* `instances` → `attributes` — закэшированные значения атрибутов.
* `dependencies` — ресурсы, от которых он зависит (см. Metadata выше).

**Rule of thumb:** никогда не редактируйте этот файл вручную. Ручные правки могут рассинхронизировать state с реальной инфраструктурой и вызвать непреднамеренный destroy/recreate при следующем `apply`.

## State and the Core Workflow

* `terraform plan` и `terraform apply` по умолчанию автоматически **обновляют (refresh)** state перед сравнением с конфигурацией — именно так обнаруживается drift (полный workflow работы с drift — в 6d).
* Terraform использует разницу между **state**, **конфигурацией** и **реальной инфраструктурой**, чтобы вычислить, что нужно изменить. Именно state делает этот diff *точечным*, а не полным сносом/пересозданием каждый раз.

## Local State (Default) vs Remote State (Preview)

По умолчанию Terraform хранит state как **локальный файл** в текущей рабочей директории. Это нормально для старта, но не работает для команд — всем нужно работать с *одним и тем же* state, чтобы избежать конфликтующих изменений.

* Механика **local backend** и **remote backends** (общий state, locking) полностью разобрана в **Section 6 (6a, 6c)** — эта заметка лишь отмечает, что такой выбор существует.

## Exam Quick Facts

* State **обязателен**, не опционален — Terraform не может надёжно управлять инфраструктурой без него.
* Три задачи state: **(1) маппинг config → реальные объекты, (2) отслеживание метаданных (зависимости, provider), (3) кэширование атрибутов для производительности.**
* Каждый реальный объект должен маппиться **ровно в один** resource instance в state.
* `plan`/`apply` по умолчанию автоматически обновляют state.
* Никогда не редактируйте state-файл вручную.
* Локальное файловое хранилище — вариант по умолчанию; общий/remote state — отдельная тема (Section 6).
