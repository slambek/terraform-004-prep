# 3e. Apply changes to infrastructure with Terraform

## Two Modes of `terraform apply`

| Mode | How | Behavior |
| :--- | :--- | :--- |
| **Automatic plan mode** | `terraform apply` (без аргумента-файла) | Генерирует новый план (как будто запущен `terraform plan`), **запрашивает подтверждение**, затем выполняет его. Поддерживает все те же режимы/опции планирования, что и `plan` (3d) — `-destroy`, `-refresh-only`, `-replace`, `-target`, `-var`, `-var-file` и т.д. |
| **Saved plan mode** | `terraform apply tfplan` | Выполняет **ровно те** действия, что записаны в ранее сохранённом файле плана — **без запроса подтверждения** (передача файла *и есть* подтверждение). Здесь нельзя добавить дополнительные режимы/опции планирования — файл плана уже зафиксировал эти решения. |

`-auto-approve` пропускает интерактивный запрос в automatic plan mode (игнорируется/не нужен с сохранённым файлом плана, поскольку он и так никогда не запрашивает подтверждение). ⚠️ Использование `-auto-approve` означает, что ни один человек не просматривает план перед его выполнением — рекомендуется, только когда вы также уверены, что ничто вне Terraform не может одновременно менять инфраструктуру.

## What Happens During an Apply

1. **Блокирует (locks)** state workspace — предотвращает параллельные запуски Terraform против того же state. Если lock уже существует, Terraform немедленно завершается с ошибкой, вместо того чтобы продолжать.
2. **Создаёт план** и ждёт подтверждения (или использует сохранённый файл плана, пропуская запрос).
3. **Выполняет** шаги плана, используя установленные providers — **параллельно, где это возможно**, **последовательно, где один ресурс зависит от другого** (см. граф зависимостей в 3d).
4. **Обновляет state** снимком нового состояния ресурсов.
5. **Разблокирует (unlocks)** state.
6. **Сообщает** о внесённых изменениях и любых значениях output.

## Error Handling During Apply

Если во время apply возникает ошибка, Terraform:

1. Логирует и сообщает об ошибке.
2. **Обновляет state-файл** теми изменениями, которые успели пройти успешно до ошибки.
3. Разблокирует state.
4. Завершает работу.

**Terraform не выполняет автоматический откат частично завершённого apply.** Ваша инфраструктура может остаться в состоянии, представляющем собой смесь старого и нового — вам нужно устранить лежащую в основе проблему и повторно применить, чтобы согласовать состояние.

Распространённые причины ошибок во время apply:

* Изменение ресурса **вне** Terraform (например, кто-то вручную удалил bucket) в промежутке между plan и apply.
* Кратковременные сетевые ошибки.
* Ожидаемая ошибка provider/API (дублирующееся имя, достижение лимита сервиса).
* Неожиданная ошибка со стороны вышестоящего сервиса (например, internal server error).
* Баг в provider'е или в самом Terraform.

Когда Terraform обнаруживает, что реальный объект изменился вне его контроля с момента последнего apply, следующий plan/apply явно сообщает об этом под заголовком **"Objects have changed outside of Terraform"**, прежде чем предложить новый набор действий для согласования.

## Replacing Individual Resources

Два флага ограничивают apply конкретными ресурсами — полная семантика флагов в 3d:

* **`-replace=ADDRESS`** — принудительно выполняет destroy-and-recreate конкретного ресурса с *той же* конфигурацией (например, для нездорового instance). Сначала выведите текущие адреса через `terraform state list`.
* **`-target=ADDRESS`** — применяет изменения только к конкретному ресурсу/модулю и его зависимостям. Зарезервировано для troubleshooting/восстановления — не для рутинного использования.

## Exam Quick Facts

* Automatic plan mode **запрашивает подтверждение**; saved plan mode — **нет** (сохранённый файл сам по себе является подтверждением).
* `apply` **блокирует state** на время выполнения и **разблокирует** его даже после ошибки.
* Apply выполняется параллельно там, где это позволяет граф зависимостей, и последовательно там, где это необходимо.
* При ошибке: state обновляется частичным прогрессом, затем Terraform **завершается без отката** — автоматической отмены нет.
* `-replace` пересоздаёт с той же конфигурацией; `-target` ограничивает apply подмножеством ресурсов — оба инструмента для исключительных случаев, а не для рутинного workflow.
