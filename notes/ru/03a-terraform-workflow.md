# 3a. Describe the Terraform workflow

## The Core Loop: Write → Plan → Apply

```text
Write   → author Terraform configuration
Plan    → preview the changes before touching anything
Apply   → provision the reproducible infrastructure
```

Это **цикл**, а не одноразовая последовательность — каждое изменение инфраструктуры запускает этот цикл заново.

> **Scope note:** эта заметка описывает *концепцию* workflow и то, как она масштабируется от отдельного практика → к команде → к HCP Terraform. Механика каждой команды (`init`, `validate`, `plan`, `apply`, `destroy`, `fmt`) разбирается отдельно в **3b–3g**.

## As an Individual Practitioner

* **Write** — редактируете конфигурацию в редакторе, выполняете `terraform init`, затем итерируете с `terraform plan` в качестве быстрого цикла обратной связи, чтобы рано отловить синтаксические ошибки.
* **Plan** — когда цикл выглядит хорошо, коммитите в систему контроля версий. `terraform apply` показывает финальный план для подтверждения перед тем, как что-либо трогать.
* **Apply** — подтверждаете через `yes`, Terraform провижинит инфраструктуру, затем вы пушите репозиторий для сохранности.

Это во многом повторяет написание кода приложения индивидуально: edit → test → commit → push.

## As a Team

Совместная работа добавляет процесс вокруг каждого шага:

* **Write** — участники команды работают в **ветках системы контроля версий**, чтобы избежать коллизий; конфликты слияния разрешаются через обычный git-workflow. Запускать планы локально становится сложнее по мере накопления sensitive input-переменных (API-ключи, сертификаты), что подталкивает команды запускать Terraform в общем **CI-окружении**, а не на индивидуальных ноутбуках.
* **Plan** — **speculative plans** (план, сгенерированный без `-out`, без намерения его применять) прикрепляются к pull request'ам, чтобы коллеги могли оценить *намерение* изменения и его *риск* до слияния — именно здесь команда решает, стоит ли вносить изменение сейчас или подождать окна обслуживания.
* **Apply** — после слияния команда просматривает финальный **concrete plan**, запущенный против общей ветки и актуального state — он может отличаться от speculative plan из PR (порядок слияния, дрейф инфраструктуры со времени ревью). Команда задаёт вопрос: нарушит ли это работу сервиса? Кому нужно об этом знать? Затем применяет изменения, иногда наблюдая за этим вместе.

Для одних команд этот цикл проходит несколько раз в неделю; для других — много раз в день.

## Enhanced by HCP Terraform

HCP Terraform не меняет три шага — он централизует и упрощает точки взаимодействия команды вокруг них:

* **Write** — централизованное, безопасное хранение **input-переменных и state**; блок `cloud` внутри `terraform {}` подключает CLI к workspace HCP Terraform, так что все участники команды планируют относительно одного и того же актуального state.
* **Plan** — автоматически запускает speculative plan при открытии PR и публикует статус прямо в PR (были изменения / изменений не было) со ссылкой на полную детализацию плана.
* **Apply** — представляет concrete plan для командного ревью/обсуждения после слияния, затем транслирует прогресс apply в реальном времени всем наблюдающим.

## Exam Quick Facts

* Трёхшаговый цикл всегда **Write → Plan → Apply** и повторяется для каждого изменения.
* **Speculative plan** = план, запущенный без намерения его реально применить (не нужен `-out`) — используется для ревью PR.
* Concrete plan, применяемый после слияния, вполне может отличаться от speculative plan, просмотренного до слияния.
* HCP Terraform улучшает (централизованный state/переменные, видимость плана в PR, живая трансляция apply) — он не заменяет основной цикл Write/Plan/Apply.
