# 8b. Describe HCP Terraform collaboration and governance features

> **Scope note:** Механика запусков (plans, applies, режимы запуска) — 8a.
> Структура workspace/project и наборы прав для проектов — 8c. Настройка
> блока `cloud`, миграция state, динамические credentials и data sources
> `tfe_outputs`/`terraform_remote_state` — 8d — этот файл покрывает *что*
> соединяют run triggers, а не механику data source.

## Core Concept

HCP Terraform добавляет поверх базового рабочего процесса Terraform
возможности, ориентированные на командную работу: общие секреты,
обязательное ревью, применение policy-as-code, видимость стоимости,
мониторинг drift/здоровья и отчётность в масштабах всей организации.

## Teams and permissions

- **Команда (team)** — это группа пользователей HCP Terraform внутри
  организации; членство хотя бы в одной команде делает вас участником
  организации.
- Команды получают права, ограниченные workspace'ами, проектами или всей
  организацией — но никогда между организациями.
- У каждой организации есть **owners team**; её участники ("owners
  организации") имеют полный доступ к организации. Создатель — её первый
  участник. Бесплатные организации ограничивают эту команду 5 участниками;
  платные — без ограничений. Вы никогда не можете удалить или опустошить
  owners team — всегда добавляйте замену перед удалением последнего
  участника.
- Команды могут иметь собственные **API-токены**, независимые от какого-либо
  пользователя.
- Управляйте командами через UI, API Teams/Team Members/Team Access или
  ресурсы provider'а `tfe_team`, `tfe_team_members`, `tfe_team_access`.

## Policy enforcement

Policy-as-code проверяет, что планы Terraform соответствуют правилам
безопасности и best practices, применяется автоматически во время
запусков.

| Framework | Notes |
|---|---|
| Terraform policy (beta) | Нативный, на основе HCL; требует Terraform ≥ v1.16alpha (нужно включить pre-releases) |
| Sentinel | Язык policy-as-code от HashiCorp |
| OPA | Open Policy Agent, использует Rego |

- **Уровни применения** (Sentinel): `advisory` (предупреждает, не блокирует),
  `soft-mandatory` (блокирует, но можно переопределить при наличии прав),
  `hard-mandatory` (всегда блокирует при провале, переопределить нельзя).
- Политики группируются в **policy sets**; набор применяется глобально или
  к конкретным проектам/workspace'ам/Stacks, и может содержать политики
  только из **одного** framework'а — при необходимости примените несколько
  наборов (разных framework'ов) к одному и тому же workspace.
- Рекомендуемый источник истины — **репозиторий VCS** (рабочий процесс
  policy-as-code: стандартизация, аудируемость); также можно писать
  политики прямо в UI или управлять наборами через API.
- И Terraform policy, и Sentinel/OPA оцениваются для **workspace'ов**;
  Sentinel и OPA **не** поддерживают Stacks — только Terraform policy
  поддерживает их, оценивая по каждому деплойменту.
- Бесплатный план включает один policy set до пяти политик; подключение
  policy sets к репозиторию VCS или управление через API требует
  Standard/Premium.

## Run tasks

Run tasks обращаются к **внешним системам** (сканеры уязвимостей,
инструменты подсчёта стоимости, кастомные проверки) между этапами plan и
apply запуска, отправляя содержимое плана и используя ответ, чтобы
разрешить или заблокировать apply. Существуют партнёрские интеграции, либо
можно построить собственную поверх API.

## Cost estimation

Перед apply workspace может показывать общую оценочную стоимость и
**дельту** стоимости, вызванную предлагаемым изменением, для основных
облачных провайдеров. Оценки стоимости также могут питать политики
Sentinel (напр. предупреждать о больших скачках стоимости). Требует
Standard/Premium; автоматически отключается для любого запуска,
использующего `-target`, поскольку targeting исключает ресурсы и дал бы
вводящую в заблуждение оценку.

## Health assessments

Автоматические проверки (Standard/Premium), удостоверяющиеся, что реальная
инфраструктура всё ещё соответствует конфигурации:

- **Drift detection** — реальные настройки vs. конфигурация Terraform. Это
  **дрейф конфигурации**, отличный от дрейфа *state*: дрейф конфигурации
  означает, что внешние изменения делают вашу конфигурацию невалидной;
  дрейф state (внешние изменения, не делающие конфиг невалидным) вместо
  этого обрабатывается операциями refresh-only (см. 6d).
- **Continuous validation** — переоценивает блоки `check` (и
  pre/postconditions) постфактум, напр. проверяя, что сайт всё ещё
  возвращает HTTP 200 или сертификат не истёк.

Требования: Terraform ≥ 0.15.4 только для drift detection, ≥ 1.3.0 для
обеих проверок; **remote или agent** execution mode; последний запуск
workspace должен быть успешным, и должен быть хотя бы один успешный apply
(проверки не выполняются на workspace без реальной инфраструктуры).

- Проверки выполняются как **неактивируемые refresh-only** планы — никогда
  не трогают реальную инфраструктуру или конфигурацию.
- Запланированы примерно каждые 24 часа от более позднего из последнего
  apply или последней проверки; можно также запустить проверку
  **по требованию** (только администратор workspace), что сбрасывает
  расписание.
- Новый запуск во время проверки **отменяет** выполняющуюся проверку.
- Ошибочный последний запуск **приостанавливает** проверки до тех пор, пока
  снова не произойдёт успешный запуск.
- Чтобы устранить обнаруженный drift: либо примените apply, чтобы
  **перезаписать** его (вернуть к конфигу), либо **обновите конфигурацию**,
  чтобы принять дрейфующее значение.

## Variable sets

Переиспользуемые группы переменных, применяемые сразу к нескольким
workspace'ам (и Stacks), определяемые на уровне **организации** или
**проекта**.

- Варианты области действия: применить глобально (владеет организация), к
  конкретным проектам/workspace'ам/Stacks, или ко всему проекту (владеет
  проект).
- **Приоритет при конфликте одного и того же ключа между двумя наборами**:
  HCP Terraform разрешает конфликт по **лексическому (алфавитному) порядку**
  имён variable set — более раннее по алфавиту имя побеждает, а другое
  показывается как "OVERWRITTEN".
- **Специфичная для workspace** переменная с тем же ключом всегда
  переопределяет значение из variable set.
- **Priority variable sets** переворачивают это ещё дальше: их значения
  переопределяют даже более специфичные области действия, включая флаги
  CLI и файлы `.tfvars`/`.auto.tfvars`.
- Workspace в режиме local execution **не** учитывают variable sets.
- Значения шифруются в состоянии покоя (Vault transit backend); описания
  хранятся в **открытом виде** — никогда не помещайте секреты в описание
  переменной.
- Предпочитайте переменные окружения переменным Terraform для credentials —
  значения переменных Terraform могут появляться в логах, state или
  Sentinel mocks.

## Private registry

Внутренне отражает опыт публичного Terraform Registry:

- **Публичные** модули/providers могут автоматически синхронизироваться в
  приватный реестр вашей организации, централизуя документацию/примеры и
  обозначая, какие из них рекомендованы организацией.
- **Приватные** модули/providers видны только внутри вашей организации (или
  организаций, настроенных для совместного доступа, в Terraform
  Enterprise).
- Реестр использует ваш **VCS** как источник истины, версионируя модули
  через Git-теги.
- Политики Sentinel могут ограничивать использование — напр. требовать,
  чтобы все не-root модули приходили из приватного/публичного реестра, или
  требовать актуальных версий.

## Explorer for workspace visibility

Общеорганизационное представление для отчётности (требует права
**Organization owner** или **View all workspaces**), охватывающее четыре
типа ресурсов: Workspaces, Modules, Providers, Terraform versions.

- Встроенные сценарии использования: топ версий модулей/providers по
  использованию, самые новые используемые версии Terraform, workspace без
  VCS, workspace с проваленными проверками, дрейфующие workspace и другое.
- Пользовательские запросы используют конструктор условий фильтрации (поле
  + оператор + значение); несколько условий комбинируются через **AND**.
- Вы можете **сохранять представления** (запрос + выбор колонок), чтобы
  вернуться к ним позже — HCP Terraform не хранит исторические результаты,
  только сам запрос; повторное открытие сохранённого представления
  выполняет его заново в реальном времени.

## Change requests

(Standard/Premium) Бэклог пунктов действий, записываемых прямо в workspace
— напр. отметка устаревшей версии модуля или необходимого исправления
безопасности — чтобы администраторы могли уведомить ответственную команду.
Создаются из запросов Explorer; владеющая команда архивирует запрос после
разрешения.

## Run triggers

Соединяет workspace с до **20 исходными workspace'ами**; любой успешный
apply в исходном workspace автоматически **ставит в очередь запуск** в
подключённом (downstream) workspace. Полезно, когда конфигурация зависит
от outputs другого workspace через data source.

- Настраивается на **downstream** workspace (требуется доступ
  администратора); также нужны права read-runs на исходный workspace.
- Запущенные таким образом запуски **не применяются автоматически** по
  умолчанию — отдельная настройка "Auto-apply run triggers" контролирует
  это независимо от обычной настройки auto-apply workspace.
- Детали поставленного в очередь запуска ссылаются обратно на исходный
  workspace и вызвавший его apply.
- Фактический кросс-workspace **доступ к данным** (чтение outputs
  источника) — отдельный механизм — см. 8d про `tfe_outputs` /
  `terraform_remote_state`.

## Exam Quick Facts

- Уровни применения Sentinel, от самого строгого к самому слабому:
  **hard-mandatory → soft-mandatory → advisory**.
- Policy set содержит политики только из **одного** framework'а за раз, но
  к workspace/Stack можно подключить несколько policy sets (разных
  framework'ов).
- Sentinel и OPA поддерживают **только workspace**; Terraform policy — это
  единственный framework, который также поддерживает **Stacks**.
- Приоритет при конфликте имён variable set — **лексический порядок имени
  набора** — не порядок создания, не специфичность области действия
  (проект vs. организация).
- **Специфичная для workspace переменная** всегда побеждает значение из
  variable set для того же ключа; **priority variable set** побеждает
  почти всё остальное, включая CLI/.tfvars.
- Health assessments требуют, чтобы **последний запуск был успешным**, и
  execution mode **remote или agent** — workspace с local execution не
  могут их использовать.
- Дрейф конфигурации ≠ дрейф state: проверки обнаруживают первое; операции
  `-refresh-only` устраняют второе.
- Run triggers требуют явного включения "Auto-apply run triggers"; иначе
  поставленный в очередь downstream-запуск всё равно ждёт ручного apply.
