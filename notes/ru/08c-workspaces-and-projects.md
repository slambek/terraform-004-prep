# 8c. Describe how to organize and use HCP Terraform workspaces and projects

> **Scope note:** Механика run/plan/apply — 8a. Команды, политики, health
> assessments, variable sets и другие возможности совместной
> работы/управления — 8b (**наборы прав** проекта, впрочем, разобраны здесь,
> поскольку они центральны для *использования* проектов). Настройка
> CLI/API-интеграции — 8d.

## Core Concept

**Workspace** — это единица управления инфраструктурой в HCP Terraform —
он объединяет конфигурацию, state и переменные так же, как это делает
постоянная рабочая директория для локального Terraform, но как объект
первого класса с разграничением прав. **Project** группирует связанные
workspace'ы (и Stacks), чтобы вы могли управлять их доступом и настройками
коллективно.

## Workspace contents

| Component | Local Terraform | HCP Terraform |
|---|---|---|
| Configuration | На диске | Репозиторий VCS или периодически загружается через API/CLI |
| Значения переменных | `.tfvars`, аргументы CLI, env оболочки | Хранятся в workspace |
| State | На диске или в удалённом backend | Хранится в workspace |
| Credentials/секреты | Env оболочки или запросы | Хранятся в workspace как sensitive-переменные |

Дополнительно HCP Terraform хранит для каждого workspace:

- **Версии state** — бэкапы каждого предыдущего файла state (для истории и
  восстановления, а не только текущий state).
- **Историю запусков** — сводку, логи, вызвавшее изменение и комментарии
  для каждого запуска.

Счётчик ресурсов workspace (показанный вверху его страницы) отражает
ресурсы из текущего файла state — **и** управляемые ресурсы, **и** data
sources.

## HCP Terraform workspaces vs. Terraform CLI workspaces

Это две разные функции, которые случайно носят одно и то же имя.

| | HCP Terraform workspaces | Terraform CLI workspaces |
|---|---|---|
| Обязательны? | Да — управлять ресурсами без хотя бы одного нельзя | Нет — полностью опциональны |
| Представляют | Полностью отдельный эквивалент рабочей директории; единицу RBAC | Несколько файлов state, разделяющих одну рабочую директорию/конфиг |
| Область действия | Все коллекции инфраструктуры в организации | Изоляция окружений (dev/staging/prod) в рамках одного конфига |

## Planning and organizing workspaces

Рекомендуемая практика: разбивайте монолитные конфигурации на более мелкие,
каждая со своим workspace и делегированным владением — напр. разделите
production-окружение на workspace'ы `networking-prod`, `app1-prod`,
`monitoring-prod`, которыми владеют разные команды. Это отражает
декомпозицию на микросервисы: команды меняют вещи параллельно, а
конфигурации становятся переиспользуемыми для других окружений (`app1-dev`
и т. д.). Администраторы Terraform Enterprise могут ограничить
максимальное число workspace на организацию.

## Projects

Каждый workspace и Stack принадлежит **ровно одному** проекту.

- Новые workspace по умолчанию попадают в **Default Project** организации
  (вы можете его переименовать, но никогда не можете удалить).
- Указывайте проект workspace при создании или переместите его позже.
- Права на уровне проекта **более гранулярны, чем на уровне организации**,
  но **шире, чем гранты на конкретный workspace** — полезно для
  ограничения команд бизнес-юнитом, отделом или технической областью без
  настройки на уровне каждого workspace.
- В организациях HCP Europe проекты создаются/управляются через саму
  платформу HCP, а не напрямую через HCP Terraform.

### Project permission sets

| Set | Grants |
|---|---|
| **Admin** | Полное администрирование проекта: чтение/изменение/удаление проекта, создание workspace в нём, перемещение workspace внутрь/наружу, управление доступом команд |
| **Maintain** | Создание/управление workspace и провижининг инфраструктуры в них — нельзя удалить проект, изменить его права или перемещать workspace внутрь/наружу |
| **Write** | Провижининг инфраструктуры только в workspace проекта — без управления workspace/проектом |
| **Read** | Просмотр только имени проекта и деталей workspace — полезно для команд, которые ссылаются на данные, не управляя ресурсами |

- Право команды на уровне организации **"Manage Workspaces"** позволяет
  пользователям создавать workspace, но новые всегда попадают в
  **Default Project**; для доступа к другим проектам нужны **"Manage
  Projects & Workspaces"** или права admin на конкретный проект.
- Право на уровне организации **"Manage all Projects"** позволяет команде
  просматривать, редактировать, удалять и назначать доступ для **каждого**
  проекта в организации.
- Общеорганизационные права (напр. "Manage all Workspaces") **имеют
  приоритет над** более узкими грантами на проект/workspace — всегда
  проверяйте доступ на уровне организации при аудите того, кто может
  дотянуться до ресурса.
- Кросс-workspace возможности, такие как совместное использование remote
  state и run triggers, ограничены теми же правами доступа — команде нужен
  доступ к **обоим** задействованным workspace, чтобы настроить связь между
  ними.

## Execution mode

Контролирует, где фактически выполняется plan/apply; настраивается на
уровне **организации**, **проекта** или **workspace**, каждый уровень по
умолчанию наследует настройку с уровня выше, если не переопределён.

| Mode | Behavior |
|---|---|
| Organization Default | Наследует настройку организации (Remote или Local) |
| Remote | Выполняется на собственной инфраструктуре HCP Terraform; полный набор возможностей совместной работы |
| Local | HCP Terraform только хранит/синхронизирует **state**; plan/apply выполняются на ваших собственных машинах |
| Agent | Хостящийся у вас агент HCP Terraform выполняет запуски, опрашивая на предмет работы — публичный входящий доступ не нужен |

Любой workspace, созданный в проекте **после** того, как вы изменили режим
execution этого проекта, наследует новое значение по умолчанию;
существующие workspace не затрагиваются. Stacks не поддерживают режим
Local execution.

## Exam Quick Facts

- Workspace в HCP Terraform **обязателен** (без него нельзя управлять
  инфраструктурой); CLI-workspace **опционален** и только изолирует файлы
  state в рамках одного конфига.
- У каждого workspace/Stack **ровно один** проект — никогда ноль, никогда
  больше одного.
- Наборы прав проекта, от самых привилегированных к наименее: **Admin →
  Maintain → Write → Read**.
- "Manage Workspaces" (право организации) всё равно направляет новые
  workspace в **Default Project** — оно не даёт доступа к другим проектам.
- Наследование execution mode: **workspace ← project ← organization**, и
  изменение режима проекта затрагивает только workspace, созданные
  **после** изменения.
- Только режимы execution **Remote или Agent** поддерживают возможности
  совместной работы HCP Terraform (Sentinel, оценка стоимости,
  уведомления, health assessments) — режим **Local** сводит workspace к
  backend'у для state.
