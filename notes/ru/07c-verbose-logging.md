# 7c. Describe when and how to use verbose logging

> **Scope note:** Здесь разбираются переменные окружения `TF_LOG*` и рабочий
> процесс диагностики/подготовки bug-репорта. Устранение неполадок,
> специфичных для state (drift, refresh) — это 6d; инспекция state через
> CLI — 7b.

## Core Concept

Terraform выводит подробные внутренние логи в stderr, когда установлена
переменная окружения `TF_LOG`. По умолчанию логирование выключено; вы
включаете его специально при диагностике неожиданного поведения или
подготовке bug-репорта, поскольку подробные логи шумные и могут содержать
sensitive-данные.

## Environment variables

| Variable | Purpose |
|---|---|
| `TF_LOG` | Главный переключатель — установите уровень, чтобы включить логирование и для core, и для providers |
| `TF_LOG_CORE` | Включить логирование только для ядра Terraform, на указанном уровне |
| `TF_LOG_PROVIDER` | Включить логирование только для плагинов provider'ов, на указанном уровне |
| `TF_LOG_PATH` | Дописывать все включённые логи в этот файл, а не только в stderr |

```bash
export TF_LOG_CORE=TRACE
export TF_LOG_PROVIDER=TRACE
export TF_LOG_PATH=logs.txt
```

- `TF_LOG_PATH` действует только если также установлен `TF_LOG` (или
  `TF_LOG_CORE`/`TF_LOG_PROVIDER`) — установка одного только пути ничего не
  включает.
- Снимите переменную (напр. `export TF_LOG_CORE=`), чтобы остановить этот
  поток логов; все они действуют только в рамках сессии и сбрасываются при
  закрытии терминала.

## Log levels

По убыванию подробности: **TRACE, DEBUG, INFO, WARN, ERROR**.

- `TRACE` — уровень, который запрашивают для **bug-репортов** — он самый
  подробный и именно то, что нужно команде Terraform для диагностики
  проблемы.
- Установка `TF_LOG=JSON` выводит логи уровня TRACE-и-выше в парсируемой
  JSON-кодировке — но этот формат явно **не является стабильным
  интерфейсом** и может измениться без предупреждения; он предназначен для
  инструментария, а не для общего использования.

## The four-layer troubleshooting model

Когда что-то идёт не так, сузьте, на каком слое возникла ошибка:

1. **Ошибки языка (HCL)** — ядро Terraform парсит вашу конфигурацию и
   напрямую сообщает номера строк и объяснение синтаксической ошибки.
2. **Ошибки state** — state рассинхронизирован с реальной инфраструктурой;
   решается через refresh, import или `-replace` (см. 6d / 7b), а не через
   логирование.
3. **Ошибки core** — баги в собственной графовой логике Terraform;
   кандидат на issue в репозитории ядра Terraform на GitHub.
4. **Ошибки provider'а** — баги в конкретном плагине provider'а (auth,
   маппинг API); сообщаются в собственный репозиторий этого provider'а.

Сначала исключите проблемы языка и state — логирование в первую очередь
полезно для диагностики слоёв **core** и **provider**.

## Bug-reporting workflow

1. Подтвердите версии: `terraform version` (также сообщает, устарели ли
   ваши CLI/providers).
2. Включите подходящий поток(и) логов на уровне `TRACE` и установите
   `TF_LOG_PATH`.
3. Воспроизведите проблему (напр. `terraform refresh`, `plan` или `apply`).
4. Просмотрите файл логов: записи, содержащие
   `provider.terraform-provider-<name>`, указывают на проблему на стороне
   provider'а; иначе это, скорее всего, core.
5. Заведите issue в правильном репозитории (ядро Terraform vs. конкретный
   provider), следуя шаблону bug-репорта этого репозитория, и приложите
   релевантный фрагмент логов.

## Exam Quick Facts

- Один только `TF_LOG_PATH` ничего не делает — нужно также установить
  `TF_LOG`, `TF_LOG_CORE` или `TF_LOG_PROVIDER`.
- `TF_LOG_CORE` и `TF_LOG_PROVIDER` позволяют изолировать, логи **какого**
  компонента вы собираете; `TF_LOG` включает оба.
- `TRACE` — уровень для использования в bug-репорте — он самый подробный.
- `TF_LOG=JSON` даёт вывод уровня TRACE в JSON, но формат явно
  нестабилен/только для инструментария, а не документированная стабильная
  схема.
- Четыре слоя диагностики, начиная с ближайшего к пользователю: **язык →
  state → core → provider** — всегда сначала исключайте язык/state, прежде
  чем предполагать баг в core или provider'е.
- Переменные окружения, установленные через `export`, действуют только в
  рамках сессии; они не сохраняются после закрытия терминала, если не
  добавлены в конфиг профиля shell.
