# 5d. Manage module versions

## The `version` Argument

```hcl
module "consul" {
  source  = "hashicorp/consul/aws"
  version = ">= 0.10.0"
}
```

* Принимает **те же операторы ограничения**, что и версии provider'ов (`>=`, `~>`, точная — см. 2a).
* **Валиден только когда `source` указывает на реестр** (публичный Terraform Registry или приватный реестр) — модули, полученные из локального пути, Git, S3, HTTP и т. д., не имеют отдельного понятия версии: это всегда тот код, который существует в этом источнике. В частности, модуль с локальным путём загружается из *того же* репозитория, что и его вызывающая сторона, и поэтому всегда разделяет версию вызывающей стороны — фиксировать отдельно нечего.
* Изменение `version` — как и изменение `source` — **требует повторного запуска `terraform init`**.
* Если вы опускаете `version` для реестрового модуля, Terraform устанавливает **самую новую** версию — крайне не рекомендуется для чего-либо помимо быстрых экспериментов, поскольку более поздний запуск может незаметно подтянуть breaking changes.

## Registry Modules Follow Semantic Versioning

Каждый модуль, опубликованный в Terraform Registry, версионируется, и версии **должны синтаксически следовать семантическому версионированию** (`MAJOR.MINOR.PATCH`); публикующим рекомендуется следовать полному смыслу semver (breaking changes повышают MAJOR), а не только синтаксису.

## ⚠️ Module Versions Are NOT Recorded in the Dependency Lock File

Это самое важное различие для экзамена по сравнению с **providers** (2a):

| | Providers | Modules |
| :--- | :--- | :--- |
| Отслеживается в `.terraform.lock.hcl`? | **Да** | **Нет** |
| Повторный запуск `init` без `-upgrade`... | ...повторно выбирает точно зафиксированную версию | ...**всегда переразрешается в самую новую версию, соответствующую ограничению** |
| Чтобы детерминированно зафиксировать версию | Полагайтесь на lock-файл | Используйте **точное** ограничение версии (без `>=`/`~>`) прямо в блоке module |

Поскольку lock-файла для модулей не существует, *единственный* способ гарантировать, что Terraform выберет одну и ту же версию модуля при каждом `init` — написать **точное ограничение**: диапазон вроде `>= 0.10.0` может незаметно разрешиться в другую (более новую) версию на машине коллеги или в CI, чем у вас.

## Resolution Behavior on `terraform init`

* Если подходящая версия модуля ещё не установлена, Terraform скачивает **самую новую версию, соответствующую ограничению**.
* `terraform init -upgrade` явно перепроверяет наличие более новых версий модулей (тот же флаг, что и для provider'ов, 3b) и обновляет установленную копию.
* Модули с локальным путём в этом смысле **вообще не версионируются** — Terraform просто перечитывает то, что сейчас на диске; редактирование файлов локального модуля вступает в силу немедленно без повторного запуска `init`/`get`.

## Upgrading a Module Version Can Break Your Configuration

Повышение `version` модуля может полностью изменить его ожидаемые входные аргументы или экспонируемые outputs — это не гипотетическая ситуация, а нормальная часть собственного семантического версионирования модуля (повышение MAJOR как раз об этом сигнализирует). После смены версии модуля:

1. Запустите `terraform init` (обязательно, так как `source`/`version` изменились).
2. Запустите `terraform validate` — ожидайте возможных ошибок **"Unsupported argument"** / **"Missing required argument"**, если интерфейс переменных новой версии изменился (механику валидации см. в 3c/4g).
3. Обновите аргументы вызывающего блока `module`, чтобы они соответствовали новому интерфейсу.
4. Повторите валидацию перед plan/apply.

## Exam Quick Facts

* `version` валиден **только** для модулей из реестра — никогда для локальных, Git, S3, HTTP и т. д.
* Версии модулей **никогда не записываются в `.terraform.lock.hcl`** — этот файл отслеживает только providers.
* Без точного ограничения `terraform init` может установить **другую, более новую** версию модуля на другой машине/при другом запуске, чем раньше — эквивалент дрейфа «без lock-файла» для модулей.
* `terraform init -upgrade` перепроверяет наличие более новых версий и для providers, **и** для модулей.
* Повышение версии модуля может изменить обязательные аргументы/outputs — всегда выполняйте `validate` заново после обновления.
