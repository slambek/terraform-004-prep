# 6c. Configure remote state using the backend block

> **Scope note:** Аргументы/флаги, специфичные для `local` backend — в 6a.
> Механика локинга — в 6b. Команды инспекции/рефакторинга state
> (`state pull`, `state push`, `state mv`, блоки `moved`/`removed`, drift) —
> в 6d.

## Core Concept

Вложенный блок `backend` внутри верхнеуровневого блока `terraform` говорит
Terraform, где хранить его state удалённо вместо локального диска, чтобы
несколько человек/автоматизаций могли разделять и блокировать один и тот же
state.

```hcl
terraform {
  backend "remote" {
    organization = "example_corp"

    workspaces {
      name = "my-app-prod"
    }
  }
}
```

## Rules & Limitations

- Конфигурация может объявлять **только один** блок `backend`.
- Блок `backend` **не может ссылаться на именованные значения** — внутри
  него нет input-переменных, locals или атрибутов data source.
- На значения, объявленные внутри блока `backend`, нельзя ссылаться в
  остальной части конфигурации.
- Если в конфигурации есть блок `cloud`, у неё **не может также быть** блока
  `backend`.
- Не настраивайте блок `backend` при использовании workspace'ов HCP
  Terraform/Terraform Enterprise — они управляют state автоматически.
- Terraform поставляется с фиксированным набором встроенных типов backend;
  вы **не можете** загружать дополнительные backend как плагины.
- Специфичные для backend аргументы (имена бакетов, токены и т. д.)
  находятся в теле блока и различаются в зависимости от типа backend —
  сверяйтесь со страницей документации конкретного backend.

## Credentials & Sensitive Data

- Избегайте хардкодинга credentials в блоке backend или через
  `-backend-config` — Terraform записывает объединённую конфигурацию
  backend в **открытом виде** в `.terraform/terraform.tfstate` (это файл
  конфигурации *backend*, а не ваш реальный state) и в любые сохранённые
  файлы плана.
- Предпочитайте переменные окружения или общепринятый файл credentials
  целевой системы.
- `terraform apply` для ранее сохранённого файла плана использует
  конфигурацию backend, **зафиксированную на момент plan**, а не текущие
  настройки — если тогда использовались времязависимые credentials, они
  могут истечь до запуска apply.

## Initializing the Backend

Каждый раз, когда вы добавляете, удаляете или меняете конфигурацию backend,
нужно заново запустить:

```bash
terraform init
```

- Это создаёт/обновляет локальную директорию `.terraform/` (никогда не
  коммитьте её — она может содержать credentials).
- `.terraform/terraform.tfstate` здесь хранит **метаданные конфигурации
  backend**, а не фактический state вашей инфраструктуры
  (`terraform.tfstate`), который находится в самом удалённом backend.
- Смена backend побуждает Terraform предложить **миграцию state** в новый
  backend, сохраняя существующий state.

## Partial Configuration

Вы можете опустить часть или все аргументы backend в конфигурации и
передать их вместо этого во время `init` — полезно, когда значения
подставляет автоматизация.

```hcl
# state.tf
terraform {
  backend "s3" {
    bucket  = ""
    key     = ""
    region  = ""
    profile = ""
  }
}
```

Способы передать остальное:

| Method | Example |
|---|---|
| File | `terraform init -backend-config="./state.config"` |
| CLI key/value | `terraform init -backend-config="KEY=VALUE"` |
| Interactive | Terraform запрашивает недостающие **обязательные** значения (никогда для опциональных) |

Отдельный **файл** конфигурации backend (не `.tf`-файл) перечисляет
атрибуты плоско, без оборачивания их в блок:

```hcl
# state.config (or recommended: *.backendname.tfbackend, e.g. config.s3.tfbackend)
bucket  = "your-bucket"
key     = "your-state.tfstate"
region  = "eu-central-1"
profile = "Your_Profile"
```

- Пары ключ/значение в CLI `-backend-config` видны в истории shell —
  избегайте их для секретов.
- При смешивании приоритет такой: опции командной строки
  **переопределяют** основную конфигурацию, а более поздние флаги
  `-backend-config` переопределяют более ранние.
- При частичной конфигурации вы всё равно должны объявить как минимум
  **пустой** блок backend с указанием типа: `backend "consul" {}`.

## Changing or Removing the Backend

- Вы можете в любой момент изменить тип backend или его аргументы;
  Terraform обнаруживает разницу и предлагает переинициализацию.
- Переконфигурирование даже *того же самого* backend всё равно выводит
  вопрос о миграции — вы можете отказаться ("no").
- При наличии нескольких workspace'ов Terraform спрашивает, копировать ли
  **все** workspace'ы в новый backend.
- Чтобы полностью убрать remote state: удалите блок `backend` и
  переинициализируйте; Terraform предложит мигрировать state обратно в
  `local`.

## Exam Quick Facts

- Только **один** блок `backend` на конфигурацию — всегда.
- Блоки `backend` **не могут** использовать ссылки на
  переменные/locals/data source — значения должны быть литеральными (или
  переданы через partial config).
- Блоки `cloud` и `backend` **взаимоисключимы**.
- Любое изменение конфигурации backend → нужно снова запустить
  `terraform init`, прежде чем заработают plan/apply/операции со state.
- Рекомендуемый способ передачи sensitive-значений — переменные окружения,
  а не литералы в `-backend-config` или хардкод в аргументах — потому что
  оба варианта сохраняются в открытом виде на диске (`.terraform/` и
  файлы плана).
- Частичная конфигурация всё равно требует непустой **метки типа** в блоке
  backend, даже если каждый аргумент пуст.
