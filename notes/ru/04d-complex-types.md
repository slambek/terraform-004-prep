# 4d. Understand and use complex types

## Type Constraints — Where They're Used

Type constraints выглядят как выражения, но это специальный синтаксис, допустимый **только** в аргументе `type` блока variable.

## Primitive Types

| Type | Meaning |
| :--- | :--- |
| `string` | Последовательность Unicode-символов. |
| `number` | Целое или дробное числовое значение. |
| `bool` | `true` / `false`. |

Terraform автоматически конвертирует между ними, когда это осмысленно: `true` ↔ `"true"`, `15` ↔ `"15"` и т.д.

## Complex Types: Collection vs. Structural

**Collection types** — группируют несколько значений **одного** типа элемента:

| Type | Description |
| :--- | :--- |
| `list(TYPE)` | Упорядоченная последовательность, индексация с 0. |
| `map(TYPE)` | Таблица поиска со строковыми ключами. |
| `set(TYPE)` | Неупорядоченная коллекция уникальных значений. |

`list` и `map` сами по себе (без аргумента типа) — сокращённая форма для `list(any)` / `map(any)` — синтаксис для совместимости с legacy; в новом коде предпочитайте явную форму.

**Structural types** — группируют значения **разных** типов по фиксированной схеме:

| Type | Schema syntax | Description |
| :--- | :--- | :--- |
| `object({KEY=TYPE, ...})` | `{ name = string, age = number }` | Именованные атрибуты, у каждого свой тип. Значение с *лишними* ключами всё равно подходит — лишнее отбрасывается при конверсии. |
| `tuple([TYPE, ...])` | `[string, number, bool]` | Последовательность фиксированной длины, требуется точное количество элементов, каждая позиция типизирована независимо. |

## Conversion Rules Between Complex Types

Terraform автоматически конвертирует между "похожими видами" везде, где это возможно:

* **Objects ↔ maps** — map (или более крупный object) конвертируется в object, если в нём есть *как минимум* требуемые ключи (лишние атрибуты отбрасываются — lossy).
* **Tuples ↔ lists** — list конвертируется в tuple, только если у него *точное* требуемое количество элементов.
* **Sets ↔ lists/tuples** — конвертация list/tuple в set убирает дубликаты и теряет порядок; конвертация set обратно в list/tuple даёт элементы в произвольном порядке (лексикографическом для строк).
* Terraform также рекурсивно конвертирует тип каждого **элемента**, используя приведённые выше правила конверсии примитивов там, где это применимо.

Если валидного пути конверсии не существует (например, конвертация tuple, содержащего вложенный list, в `map(string)`), Terraform выдаёт **ошибку несовпадения типов**.

## The `any` Constraint

`any` — это **плейсхолдер**, а не настоящий тип — Terraform пытается найти один конкретный тип, удовлетворяющий каждому использованию значения.

⚠️ **Используйте `any` только тогда, когда передаёте значение насквозь, не трогая его** (например, прямо в `jsonencode()`), никогда не обращаясь к его внутренней структуре. Если ваш модуль как-либо инспектирует, индексирует или проверяет тип значения — вместо этого пишите точный тип.

С коллекцией вроде `list(any)` Terraform выводит единый тип элемента для *всего* списка — например, `["a", "b", "c"]` → `list(string)`; смешанный `["a", 1, "b"]` всё равно разрешается в `list(string)` через конверсию примитивов; но `["a", [], "b"]` завершается ошибкой, потому что у строки и пустого tuple нет общего типа.

## Optional Object Attributes

Пометьте атрибут `object` как опциональный с помощью модификатора `optional(...)` внутри схемы типа:

```hcl
variable "with_optional_attribute" {
  type = object({
    a = string                # required
    b = optional(string)      # optional, defaults to null if omitted
    c = optional(number, 127) # optional, defaults to 127 if omitted
  })
}
```

* `optional(TYPE)` — без default → отсутствие/`null` становится `null`.
* `optional(TYPE, DEFAULT)` — Terraform подставляет `DEFAULT` как когда атрибут **отсутствует**, так и когда он **явно установлен в `null`** — так что нижестоящему коду никогда не нужно проверять его на null.
* Defaults применяются **сверху вниз** через вложенные optional-структуры — сначала применяется внешний default, затем любые вложенные defaults внутри него.
* Чтобы динамически решить *не* устанавливать опциональный атрибут, используйте условное выражение с `null` в одной из веток: `error_document = var.legacy_filenames ? "ERROR.HTM" : null` — это оставляет атрибут неустановленным, и вступает в силу собственный default модуля.

## Exam Quick Facts

* Примитивные типы: `string`, `number`, `bool` — автоматически конвертируются друг в друга, если содержимое строки валидно.
* Collection types (`list`, `map`, `set`) содержат **один** тип элемента; structural types (`object`, `tuple`) содержат **смешанные** типы по фиксированной схеме.
* Конверсия object → map (и наоборот) может быть **lossy** — лишние ключи отбрасываются.
* `any` — плейсхолдер, разрешающийся в один конкретный тип — никогда не используйте его просто чтобы не писать настоящий type constraint.
* `optional(TYPE, DEFAULT)` подставляет default как при отсутствии, **так и** при явном `null` — гарантируя non-null значение внутри модуля.
