## Core Concept

HCP Terraform — это управляемое приложение, которое запускает Terraform за
вас в согласованной, общей удалённой среде вместо вашей рабочей станции.
Оно организует работу в **workspaces**, выполняет **runs** (plan, затем
apply) применительно к ним и добавляет поверх обычного рабочего процесса
Terraform слои review, хранения секретов и политик.

## Three ways to trigger runs

| Workflow | How it works |
|---|---|
| **VCS-driven** (основной) | Workspace связан с репозиторием; мерджи в отслеживаемую ветку автоматически запускают plan+apply; pull request'ы автоматически запускают speculative plan и публикуют check |
| **CLI-driven** | Локальные `terraform plan`/`apply` выполняются **удалённо** в HCP Terraform, стримя логи обратно в ваш терминал, используя CLI-интеграцию (блок `cloud`) |
| **API-driven** | Любой инструментарий управляет запусками через API HCP Terraform — максимально гибко, требует больше всего настройки |

Интеграция с VCS опциональна — без неё вы всё равно можете получить
удалённое выполнение и другие возможности HCP Terraform через API или CLI.

## Remote operations

По умолчанию (**Execution Mode: Remote**) HCP Terraform запускает Terraform
на своих собственных одноразовых виртуальных машинах, а не на вашей рабочей
станции. Именно это открывает проверки политик Sentinel/OPA, оценку
стоимости, уведомления и согласованную видимость запусков. Execution mode —
это настройка workspace/project — режимы **Local** и **Agent** см. в 8c.

## Runs and workspaces

Каждый запуск происходит **в контексте workspace**, который предоставляет
конфигурацию, переменные и state — ту же роль, что для локального Terraform
играет постоянная рабочая директория.

- Каждый workspace хранит **очередь** запусков и обрабатывает их по
  порядку; новый запуск остаётся **pending**, пока не завершится текущий,
  поскольку выполняющийся запуск может изменить то, что должен делать
  более поздний запуск.
- Запуск run **блокирует** workspace на конкретную версию конфигурации и
  набор переменных — последующие изменения переменных/кода влияют только
  на будущие запуски, а не на те, что уже в очереди/планируются/ожидают
  apply.
- Два типа операций **игнорируют** и очередь, и локи workspace: **plan-only
  запуски** и **этап планирования** запусков с сохранённым планом (сам
  apply сохранённого плана всё равно блокирует/встаёт в очередь как
  обычно).

## Plan and apply

HCP Terraform всегда сначала планирует, а затем применяет точный вывод
этого плана — он никогда не переизобретает apply с нуля.

- По умолчанию он **ждёт одобрения пользователя** перед apply; workspace
  можно настроить на **auto-apply** успешных планов вместо этого.
- Некоторые планы никогда не могут применяться автоматически: те, что
  поставлены в очередь run trigger'ами, или поставленные пользователем без
  прав на apply для этого workspace.
- План **без изменений** завершается как "Planned and finished" — HCP
  Terraform не выполняет шаг apply для no-op плана (**allow empty apply** —
  режим запуска, явно переопределяющий это — см. ниже).

## Speculative plans

Plan-only запуски, используемые для предварительного просмотра изменений
во время редактирования/ревью — они никогда не применяются.

- Не ждут очереди запусков, поскольку не могут повлиять на реальную
  инфраструктуру.
- Три триггера: pull request в VCS (публикует check со ссылкой на план),
  локальный запуск `terraform plan` с настроенной CLI-интеграцией, или
  API-запуск для версии конфигурации, помеченной как `speculative`.
- Проваленный/отменённый speculative plan можно **повторить** (та же версия
  конфигурации), если у вас есть право ставить планы в очередь для этого
  workspace.

## Saved plans

*Требует Terraform CLI ≥ 1.6.0 для CLI-рабочего процесса.*

```bash
terraform plan -out <FILE>
terraform apply <FILE>
terraform show <FILE>       # inspect before applying
```

- В отличие от обычных запусков, **этап планирования** пропускает очередь
  запусков (как plan-only запуски); **применение** всё равно требует, чтобы
  workspace был разблокирован, и ведёт себя как обычный запуск с очередью
  и локом.
- **Никогда не применяется автоматически**, даже если у workspace включён
  auto-apply — он применяется только по ручному подтверждению.
- HCP Terraform **автоматически отбрасывает** сохранённый план, если другой
  запуск применяется (или state иначе изменяется) до того, как вы его
  подтвердите, или если он висит неподтверждённым несколько недель.

## Other run modes

Выбираются через флаг CLI, опцию API или выпадающий список типа запуска в
UI:

| Mode | Purpose |
|---|---|
| Destroy | Планирует уничтожение всех объектов независимо от конфига |
| Refresh-only | Обновляет state, чтобы соответствовать реальной инфраструктуре, не меняя инфраструктуру (механику на уровне CLI см. в 6d) |
| Allow empty apply | Позволяет применить no-op план — используется, чтобы форсировать **обновление версии state**, напр. после повышения версии Terraform для workspace |
| Replace | Форсирует destroy+recreate конкретных ресурсов (`-replace=ADDRESS`) |
| Targeted | Ограничить план конкретными адресами ресурсов — только для исключительного использования |

## Workspace Terraform version

У каждого workspace есть назначенная версия Terraform, используемая для
**всех** его удалённых запусков, что обеспечивает согласованное поведение.
Новые workspace по умолчанию получают самую новую версию; workspace,
мигрированный из локального state, наследует версию CLI, использованную во
время миграции. Вы можете:

- В любой момент изменить версию workspace в его настройках.
- Переопределить версию **только для speculative plan**, чтобы протестировать
  совместимость с обновлением до того, как зафиксировать изменение для
  всего workspace.
- После повышения major-версии, меняющей формат файла state, запустить run
  с **allow-empty-apply**, чтобы обновить сохранённую версию state, даже
  если нет изменений инфраструктуры для внесения.

## Exam Quick Facts

- VCS-driven — основной/дефолтный рабочий процесс; CLI-driven и API-driven
  — альтернативы, когда вы не хотите связывать репозиторий.
- Workspace обрабатывает запуски **строго по порядку** — новые запуски
  ждут в статусе "pending", если только это не plan-only или этап
  планирования сохранённого плана.
- Speculative plans **никогда нельзя применить** — они существуют
  исключительно для предпросмотра изменений и запуска проверок политик во
  время ревью.
- Сохранённый план автоматически отбрасывается, если state workspace
  меняется до того, как вы его подтвердите, или после слишком долгого
  ожидания без подтверждения.
- No-op планы не применяются автоматически сами по себе — **allow empty
  apply** — это конкретный режим запуска, форсирующий apply в любом случае,
  в основном для обновлений версии state.
- Блокировка workspace фиксирует запуск на конкретной версии конфига +
  значениях переменных; изменение любого из них впоследствии влияет только
  на *будущие* запуски.
