# 4f. Define resource dependencies in configuration

> **Scope note:** внутренняя механика графа (типы узлов, порядок построения/обхода, `-parallelism`) разобрана в **3d**. Эта заметка сфокусирована на двух способах, которыми *вы* объявляете зависимость в конфигурации, и их практическом эффекте.

## Implicit Dependencies (the Default, Preferred Way)

Terraform автоматически выводит зависимость всякий раз, когда конфигурация одного ресурса **ссылается на атрибут другого ресурса**:

```hcl
resource "aws_instance" "example_a" { }

resource "aws_eip" "ip" {
  instance = aws_instance.example_a.id   # implicit dependency
}
```

Поскольку `aws_eip.ip` ссылается на `aws_instance.example_a.id`, Terraform знает, что должен полностью создать `example_a` перед созданием `ip`. Ресурс, у которого **нет** такой ссылки (например, `aws_instance.example_b` рядом с приведённым выше), не имеет ограничений по порядку и может быть создан **параллельно**.

Это основной и предпочтительный способ, которым Terraform понимает связи — он не требует дополнительного синтаксиса, достаточно просто естественным образом написать ссылку.

## Explicit Dependencies (`depends_on`)

Иногда реальная зависимость существует, но не видна ни через одну ссылку на атрибут — например, приложение на EC2-instance ожидает, что уже существует определённый S3-bucket, при этом ничто в Terraform-конфигурации для instance фактически не ссылается на bucket. Используйте `depends_on` на блоке resource или module, чтобы принудительно задать порядок:

```hcl
resource "aws_s3_bucket" "example" {}

resource "aws_instance" "example_c" {
  depends_on = [aws_s3_bucket.example]
}

module "example_sqs_queue" {
  source     = "terraform-aws-modules/sqs/aws"
  depends_on = [aws_s3_bucket.example, aws_instance.example_c]
}
```

`depends_on` принимает **список**, поэтому один ресурс/модуль может ждать сразу нескольких других.

`depends_on` также поддерживается в блоках `data` (см. 4a) и `output` (см. 4c) — в обоих случаях он заставляет вычисление ждать перечисленную зависимость, а на блоке data ещё и откладывает чтение, как описано в 4a.

⚠️ **Стоимость:** поскольку Terraform ждёт полного завершения перечисленного ресурса перед началом зависимого от него, добавление явных зависимостей может **увеличить общее время apply**, убирая параллелизм, который иначе был бы возможен.

## Dependencies Affect Both Create *and* Destroy Order

Те же рёбра графа, используемые для создания, используются — в обратном порядке — для уничтожения. Возьмём пример с S3-bucket выше: при `terraform destroy` SQS-очередь и EC2-instance (оба зависящие от bucket) уничтожаются **до** самого bucket, хотя bucket был создан первым.

## What Does *Not* Affect Order

**Порядок объявления ресурсов в файле конфигурации никак не влияет** на порядок, в котором Terraform их создаёт или уничтожает — только граф зависимостей (неявные ссылки + `depends_on`) определяет порядок выполнения.

## Exam Quick Facts

* Implicit dependency = ссылка на атрибут другого ресурса в выражении — механизм по умолчанию, предпочтительный.
* Explicit dependency = `depends_on = [...]`, используется только когда реальная зависимость существует, но не видна ни через одну ссылку на атрибут.
* `depends_on` работает на блоках `resource`, `module`, `data` и `output`.
* Явные зависимости **стоят времени apply** — они убирают иначе доступный параллелизм.
* Порядок зависимостей управляет **как** create, так и destroy — destroy идёт в обратном порядке.
* Порядок объявления в `.tf`-файле не имеет значения для порядка выполнения.
