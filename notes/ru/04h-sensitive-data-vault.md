# 4h. Manage sensitive data, including secrets management with Vault

## The Core Problem

Файлы state и plan могут содержать **подробные данные инфраструктуры**, включая секреты (пароли, токены) — и по умолчанию Terraform хранит state в виде **открытого текста** локально. Terraform даёт вам три разных инструмента в зависимости от того, что вам реально нужно:

| Goal | Tool |
| :--- | :--- |
| Скрыть значение из вывода CLI/UI, но при этом нормально хранить его в state | `sensitive = true` (variable/output) |
| Вообще никогда не хранить значение в файлах state или plan | `ephemeral = true`, блок `ephemeral` или write-only аргумент |
| Получить/управлять самим секретом (а не просто скрыть его) | Внешний инструмент управления секретами, например **Vault provider** |

## `sensitive` — Redact From Output, Still Stored in State

```hcl
variable "database_password" {
  type      = string
  sensitive = true
}
```

* Скрывает значение (и всё, что из него производно) в выводе CLI при `plan`/`apply` — отображается как `(sensitive value)`.
* **Всё равно фиксируется в открытом виде в файлах state и plan.** `terraform output -json` / `-raw` также раскрывают его в открытом виде (см. 4c).
* Если нужно и скрытие, *и* отсутствие хранения, сочетайте `sensitive` с `ephemeral` (ниже) на переменной или output дочернего модуля.

## Ephemeral Values — Omit From State and Plan Entirely (Terraform 1.10+)

Ephemeral-значения существуют только во время **выполнения**; Terraform никогда не записывает их в файлы state или plan. Поскольку ничего не сохраняется, любое значение, которое вы действительно хотите оставить (например, сгенерированный пароль), нужно зафиксировать в отдельном, не-ephemeral ресурсе/output, если оно понадобится позже.

Четыре способа создать ephemeral-значение:

1. **Аргумент `ephemeral` на переменной** — может использоваться в других ephemeral-контекстах (например, в блоке `provider`).
2. **Аргумент `ephemeral` на output дочернего модуля** — **не допускается на outputs root-модуля.**
3. **Блок `ephemeral`** — объявляет временный ephemeral-*ресурс* (например, `ephemeral "random_password" "db_password" {}`), существующий только для текущей операции.
4. **Write-only аргумент на управляемом ресурсе** (Terraform 1.11+) — определяется provider'ом, по соглашению называется `..._wo` с парным целочисленным `..._wo_version`. Provider использует значение во время операции, затем Terraform его отбрасывает — оно никогда не сохраняется.

```hcl
ephemeral "random_password" "db_password" {
  length = 16
}

resource "aws_db_instance" "example" {
  password_wo         = ephemeral.random_password.db_password.result
  password_wo_version = 1   # bump this to signal the value changed
}
```

Поскольку Terraform не может "сравнить" write-only значение (оно никогда не хранится), парный аргумент `_version` — это то, как вы сообщаете Terraform, что значение изменилось — его увеличение заставляет provider использовать новое значение в следующем apply.

На ephemeral-значения можно **ссылаться** только в ограниченном наборе контекстов: `locals`, другая ephemeral-переменная, ephemeral-output дочернего модуля, write-only аргумент ресурса, другой блок `ephemeral`, конфигурация блока `provider`, и блоки provisioner/connection.

## Vault Provider — Injecting Real Secrets, Not Just Hiding Them

**Vault provider** позволяет Terraform читать из, записывать в и настраивать HashiCorp Vault — обычно используется для получения **короткоживущих, динамически сгенерированных credentials** (например, ограниченных по scope ключей AWS IAM) вместо хранения долгоживущих статичных credentials на машине разработчика или в конфигурации.

**Pattern:** Vault Admin настраивает AWS Secrets Engine + Vault role (ограниченная IAM policy, короткий TTL) в Vault; конфигурация Terraform Operator'а затем запрашивает короткоживущие AWS credentials у этой Vault role во время plan/apply и использует их для настройки provider'а `aws` — Terraform никогда не касается долгоживущего AWS-ключа.

**Benefits:** операторы управляют одной Vault role вместо множества долгоживущих, широко ограниченных статичных credentials; утёкший ограниченный по запуску credential полезен только на время своего TTL; права можно централизованно ужесточить, отредактировав Vault role, что немедленно ограничивает возможности будущих запусков Terraform.

**Caveats:**

* У Terraform по-прежнему **нет механизма скрытия секретов, прочитанных через provider/data source** — всё, прочитанное из Vault (или записанное в него), фиксируется **в открытом виде в файлах state и plan**, точно так же, как и любое другое значение. Относитесь к этим файлам как к sensitive независимо от участия Vault.
* TTL сгенерированного токена/credential должен быть достаточно длинным, чтобы покрыть **весь** apply — если apply (или ожидание подтверждения) длится дольше TTL, credentials истекают посреди выполнения, и операция завершается ошибкой. Увеличение TTL для компенсации также расширяет окно уязвимости в случае утечки credential — это реальный компромисс, а не бесплатное решение.

## State Security Best Practices (Applies Regardless of Sensitivity Tooling)

Поскольку `sensitive`, неправильно использованные ephemeral-значения и даже секреты из Vault всё равно могут оказаться в state:

* **Храните state удалённо**, а не как локальный файл в открытом виде.
* **Шифруйте state в состоянии покоя** — например, HCP Terraform шифрует автоматически и позволяет предоставить собственные ключи; backend S3 может шифровать через `encrypt = true`; GCS поддерживает управляемые заказчиком ключи.
* **Используйте контроль доступа**, чтобы ограничить, кто может читать state.
* **Используйте журналы аудита**, чтобы отслеживать доступ к state со временем.
* Никогда не коммитьте файлы `.tfvars`, содержащие секреты, или файлы плана (бинарные или JSON — см. 3d), в систему контроля версий.

## Exam Quick Facts

* `sensitive` скрывает значения **только из вывода CLI/UI** — значение всё равно присутствует в файлах state/plan в открытом виде.
* `ephemeral` (variable/output/block) и write-only аргументы ресурса (`_wo` + `_wo_version`) — единственные способы **полностью** исключить значение из файлов state и plan.
* Outputs `ephemeral` — только для дочерних модулей — никогда не валидны на root-модуле.
* Парный аргумент `_version` write-only аргумента — это то, как вы сигнализируете "это значение изменилось", поскольку Terraform не может сравнить значение, которое никогда не хранит.
* Vault provider предоставляет **короткоживущие, динамически ограниченные** credentials вместо долгоживущих статичных — но **не** скрывает ничего, что он читает/пишет из state или plan-файлов.
* Независимо от инструментария, относитесь к файлам state и plan как к sensitive-артефактам: храните удалённо, шифруйте в покое, ограничивайте доступ, ведите аудит.
