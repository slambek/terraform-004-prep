# 4a. Use and differentiate `resource` and `data` blocks

## Core Distinction

```text
resource block → creates AND manages a real infrastructure object (CRUD)
data block     → READS existing information only — never creates or modifies
```

**Resource** — это любой объект инфраструктуры, полным жизненным циклом которого вы хотите, чтобы владел Terraform. Какие типы ресурсов доступны, полностью зависит от того, какие **providers** установлены (см. 2a–2c).

## What Happens to Resources on `apply`

При apply конфигурации Terraform выполняет то из перечисленного, что нужно, чтобы согласовать конфигурацию с реальностью:

1. **Создаёт** ресурсы из конфигурации, которых ещё не существует как реальных объектов.
2. **Уничтожает** ресурсы, которые есть в state, но больше не в конфигурации.
3. **Обновляет на месте** ресурсы, чьи аргументы изменились, если API provider'а поддерживает обновление этого аргумента на месте.
4. **Уничтожает и пересоздаёт** ресурсы, чьи изменённые аргументы *нельзя* обновить на месте (ограничение реального API — схема provider'а помечает такие аргументы как "force new").
5. **Обновляет state-файл**, чтобы конфигурация, реальная инфраструктура и state совпадали.

## Data Sources

Блок `data` связан ровно с **одним** data source и может только **читать** из него — никогда не создавать и не изменять. Документация provider'а определяет, какие data sources существуют и какие аргументы/атрибуты поддерживает каждый.

```hcl
data "aws_ami" "example" {
  most_recent = true
  owners      = ["self"]
  tags = {
    Name = "app-server"
  }
}
```

Ссылайтесь на результат через `data.<TYPE>.<LABEL>.<ATTRIBUTE>`, например `data.aws_ami.example.id`.

## When Terraform Reads a Data Source: Plan vs. Apply

Terraform *пытается* опросить data sources во время фазы **planning**, но **откладывает чтение до фазы apply**, когда не может заранее предсказать аргументы, необходимые для выполнения запроса. Это происходит, когда:

* Блок data зависит (напрямую или через `local`) от **управляемого Terraform ресурса**, который запланирован к изменению в текущем плане.
* `precondition`/`postcondition` на блоке data зависит, прямо или косвенно, от изменяющегося ресурса.
* Аргумент в блоке data ссылается на значение, которое можно вычислить **только во время apply**.

При откладывании интерполированные атрибуты data source отображаются в плане как `(known after apply)`, а нижестоящие ресурсы, ссылающиеся на эти данные, не могут быть провижинены до apply. Когда ни один из аргументов блока data не зависит от неразрешённых значений, Terraform читает его во время обычного шага **refresh** (до planning), так что diff отражает реально полученные значения.

⚠️ Добавление `depends_on` на блок data в Terraform ≥0.13 всегда откладывает чтение до apply — более ранние версии (0.12 и ниже) могут давать непредвиденное поведение с этим паттерном.

## Specialized / Local-Only Data Sources

Некоторые data sources вообще не опрашивают внешнюю инфраструктуру — они генерируют данные, которые существуют только для текущей операции и пересчитываются при каждом plan:

* `template_file` (HashiCorp provider `template`) — рендерит шаблон.
* `local_file` (HashiCorp provider `local`) — читает локальный файл.
* `aws_iam_policy_document` (provider `aws`) — рендерит JSON-документ IAM policy.

## Meta-Arguments Available on Both Block Types

И `resource`, и `data` блоки принимают несколько нативных для Terraform **мета-аргументов**, которые управляют *тем, как* Terraform их создаёт/читает, а не *тем, что* они собой представляют. Каждый из них подробно разобран в другом месте этой подготовки:

* `count` / `for_each` — несколько instance (4b/4d).
* `provider` — альтернативная/aliased конфигурация provider'а (2b).
* `depends_on` — явная зависимость (4f).
* `lifecycle` (подблоки `precondition`/`postcondition`) — кастомная валидация (4g).

## Exam Quick Facts

* `resource` = полный CRUD-lifecycle; `data` = **только чтение**, никогда не создаёт/не изменяет.
* Apply может выполнить до 5 действий на ресурс: create, destroy (удалён из конфигурации), обновление на месте, destroy-and-recreate (принудительная замена), синхронизация state.
* Чтение data source откладывается до **apply** только тогда, когда его аргументы зависят от значений, ещё не известных во время plan.
* Добавление `depends_on` на блок data **всегда** заставляет читать во время apply (Terraform 0.13+).
* Специализированные data sources (`template_file`, `local_file`, `aws_iam_policy_document`) генерируют/читают локальные данные, а не state реальной инфраструктуры.
