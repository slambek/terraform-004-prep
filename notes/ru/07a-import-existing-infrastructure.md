# 7a. Import existing infrastructure into your Terraform workspace

> **Scope note:** Этот файл покрывает первичный ввод под управление
> инфраструктуры, которой Terraform никогда раньше не управлял (команда
> `terraform import` и управляемый конфигом рабочий процесс с блоком
> `import`). Совместное использование `import` + `removed` для миграции
> ресурса, который *уже* управляется Terraform, из одного файла state в
> другой, разобрано в 6d — не воспроизводите этот процесс здесь заново,
> просто отметьте, что такая команда существует.

## Core Concept

Импорт привязывает существующий реальный объект к адресу ресурса в state
Terraform, чтобы Terraform мог управлять его полным жизненным циклом
дальше. Terraform может инспектировать только **текущие** атрибуты объекта
— он не может импортировать состояние здоровья, изначальное намерение или
историю, и он не определяет за вас связи между ресурсами.

## Two ways to import

| Approach | Command/config | Notes |
|---|---|---|
| Legacy CLI | `terraform import ADDRESS ID` | Императивный, по одному ресурсу за раз, без предварительного просмотра плана |
| Config-driven (≥ 1.5) | блок `import` + `terraform plan`/`apply` | Безопаснее: можно просмотреть заранее, дружелюбен к CI/CD, может автогенерировать конфиг |

### `terraform import` (CLI)

```bash
terraform import aws_instance.foo i-abcd1234
terraform import module.foo.aws_instance.bar i-abcd1234
terraform import 'aws_instance.baz[0]' i-abcd1234              # count
terraform import 'aws_instance.baz["example"]' i-abcd1234      # for_each
```

- **ADDRESS** — это любой валидный адрес ресурса (в root или внутри модуля).
- Формат **ID** специфичен для ресурса/провайдера (напр. ID EC2-инстанса vs.
  ID Route53-зоны) — сверяйтесь с документацией провайдера.
- Импортирует **только один ресурс за раз** — он не может импортировать
  целую коллекцию (напр. весь VPC) за один вызов.
- У вас уже должен быть (возможно, пустой) соответствующий блок `resource`
  в конфигурации перед импортом — вы можете оставить аргументы
  незаполненными и заполнить их позже, ориентируясь на вывод
  `terraform plan`.
- Требует, чтобы конфигурация provider'а была разрешима из `.tf`-файлов в
  `-config` (по умолчанию — рабочая директория), переменных окружения или
  интерактивных запросов. Конфигурация provider'а, используемая для импорта,
  **не может зависеть от data source** — только от переменных.

Полезные флаги:

| Flag | Purpose |
|---|---|
| `-config=path` | Директория конфига, который настраивает provider (по умолчанию: cwd) |
| `-var` / `-var-file` | Передать значения переменных (актуально только вместе с `-config`) |
| `-lock=false`, `-lock-timeout` | Управление локингом во время операции |
| `-provider=provider` | *Устарел* — переопределить provider, используемый для импорта |
| `-ignore-remote-version` | Только для CLI-интеграции HCP Terraform / backend `remote` |
| `-state`, `-state-out`, `-backup` | Legacy, **только для local backend** |

### Complex imports

Некоторые ресурсы импортируются больше чем в одну запись state — напр.
импорт AWS network ACL также создаёт по одной записи state
`aws_network_acl_rule` на каждое правило. Эти вторичные ресурсы ещё не
существуют в вашей конфигурации, поэтому вам нужно самостоятельно добавить
соответствующие блоки resource, иначе Terraform запланирует их
**уничтожение** при следующем запуске.

### Config-driven import (`import` block)

```hcl
import {
  id = "i-abcd1234"
  to = aws_instance.example
}
```

И `id`, и `to` обязательны. Рабочий процесс:

1. Добавьте блок `import` (в любом месте конфигурации).
2. Запустите `terraform plan -generate-config-out=generated.tf` — Terraform
   находит объект и записывает полный блок resource (каждый аргумент,
   включая значения по умолчанию) в указанный файл. **Этот файл не
   применяется автоматически** — его нужно просмотреть, отредактировать и
   перенести в ваш реальный конфиг перед коммитом.
3. **Проредите** сгенерированный конфиг до обязательных аргументов и любых
   значений, отличающихся от значений по умолчанию provider'а; если
   оставить каждый сгенерированный аргумент, это может вызвать нежелательные
   diff'ы или замены (напр. значение `null` по умолчанию, которое provider'у
   на самом деле нужно как `[]`).
4. Заново запустите `terraform plan`, чтобы подтвердить, что план теперь
   представляет собой **no-op импорт** (или только неразрушающие изменения
   на месте), прежде чем применять.
5. `terraform apply` выполняет импорт и все накопленные изменения вместе —
   в отличие от CLI-формы, config-driven импорт может импортировать *и*
   изменять ресурс за один шаг.

## Limitations

- Импорт использует только **текущее** сообщаемое состояние инфраструктуры
  — он не может рассказать вам о здоровье, изначальном намерении или
  неуправляемом состоянии файловой системы, например, внутри контейнера.
- Не генерирует связи/зависимости между ресурсами — добавляйте `depends_on`
  или ссылки самостоятельно.
- Не сообщает, какие атрибуты по умолчанию безопасно опустить — вы решаете
  это сами во время прореживания.
- Не все providers/ресурсы поддерживают импорт.
- Импорт ресурса не гарантирует, что Terraform сможет безопасно уничтожить
  и пересоздать его — он может зависеть от неуправляемой инфраструктуры.
- Делайте бэкап state перед импортом новой инфраструктуры.

## Exam Quick Facts

- `terraform import` привязывает **ровно один** ресурс за вызов — никогда
  целую коллекцию.
- Соответствующий (даже пустой) блок `resource` **уже должен существовать**
  в конфигурации перед запуском `terraform import ADDRESS ID`.
- Вывод `-generate-config-out` из config-driven импорта — это **отправная
  точка**: применение его без прореживания обычно вызывает нежелательные
  замены.
- Блок `import` требует ровно два аргумента: `id` и `to`.
- Complex imports создают дополнительные записи state, которые нужно
  вручную отразить в конфиге, иначе Terraform запланирует их уничтожение.
- `-state`/`-state-out`/`-backup` в `terraform import` применимы только к
  **local** backend; `-ignore-remote-version` применим только к backend
  `remote` / CLI-интеграции HCP Terraform.
